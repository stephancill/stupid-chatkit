# Design

StupidChatKit is the chat framework of [stupid social](https://github.com/stephancill/stupid-social), as a library. This document is the design and the reasons for it; `README.md` shows how an app uses it.

## What an app supplies

The kit knows no network and imports nothing of an app. An app supplies:

- Its networks, as `ChatNetwork` ids (an app adds them as static members, such as `static let telegram = ChatNetwork(rawValue: "telegram")`). The framework only compares them; `ChatNetwork` encodes as its string.
- Its destination type, the app's id for a chat across its networks. The Chats list types are generic over it (`ChatSummary<Destination>`, `ChatListPage`, `ChatListSource`, `ChatListViewModel`, `ChatListProvider<Destination>`); an app typically declares aliases with the same names. A file that imports both the kit and a module declaring those aliases gets "ambiguous for type lookup"; import only the module with the aliases (it can re-export the kit with `@_exported import StupidChatKit`).
- At launch, through `ChatKit`: `onEvent` (`ChatEvent`s, for usage metrics), `networkIcon` (a network's icon beside a chat's title and in a post's corner), `openAppLink` (links the app opens itself instead of the browser) and `resolveLink` (what to draw in place of a link, in every chat). Each defaults to doing nothing.
- Resolved links: `ChatViewModel` passes each message the network publishes through `resolveLink` before showing it. An embed it returns takes the place of the card or link preview whose link it was asked for, and is added after the embeds for a web link only in the text; an embed shows once per message. The app answers from memory, starts loading what it doesn't have, and calls `linksDidResolve()` when it arrives, which draws open chats again from what the networks last published. So a post link reads the same in every chat, whatever preview its network sends, without each adapter knowing about other networks' posts. The Chats list asks `resolveLink` for the links in each row preview as it changes, so a post in a message that arrived while away has loaded before its chat opens (loading ahead stores messages without rendering them, so it can't).
- Videos: tapping one downloads it whole and plays the file, except an HLS playlist (`.m3u8`), which streams, since a downloaded playlist can't reach its segments.
- Saving an image: the image viewer's save button saves the original bytes to Photos, or on a Mac (`isiOSAppOnMac`) into Downloads, as Mac apps save. `ChatDownloads.save(_:from:)` (public, so apps save their own files the same way) asks once for the Downloads folder, since an iPhone app on a Mac is sandboxed, keeps it as a security-scoped bookmark, and copies files straight in from then on.
- Post media: a `.post` embed's photos and videos (and its quoted post's thumbnail) open through `ChatKit.openPostMedia` when the app sets it, so an app can show them in its own viewer (with the post's counts and actions); otherwise in the chat's image viewer and video player.
- Chat media: when the app sets `ChatKit.openChatMedia`, tapping a photo or video that fills a bubble opens a `ChatMediaGallery`: every such photo and video in the loaded messages (`ChatMediaItem.items(in:)`, oldest first, keyed `<message id>#<embed index>`), the media again whenever `messages` changes, and `loadEarlier` for paging back past the first. Link previews' and posts' media and stickers stay out, so they open as before. Unset, each opens alone in the chat's image viewer or video player.
- Optionally, reminders (`ChatReminders` on `ChatViewModel.reminders`, with the `ChatReminderDelay` presets): the kit offers Remind Me and Mark as Done, and the app keeps and delivers them.
- A `ChatListProvider` that isn't connected throws a `ChatNotConnectedError` whose `isNotConnected` is true: it lists nothing and shows no error.
- "Redact names" (people's names show as "Redacted", for screenshots) is on while the `UserDefaults` bool at `ChatRedaction.defaultsKey` is true.

## Chat Framework

Chat is one framework with an adapter per chat network (in stupid social: Apron, Telegram, Instagram Direct, Spotify Messages, X Chat, Bluesky, Discord, LinkedIn). The framework owns everything a user would expect to behave the same in every chat; an adapter only translates between its network and the framework's models. This section is written without platform specifics so another client of the same networks can follow it.

**Framework (shared):**

- Display models: message, user, embed (image, video, file, card, link preview with media, social network post, audio, voice message with waveform, sticker, pending upload), reaction totals, reactors, attachment. Media embeds name a URL the platform's loader can fetch, the network's own scheme included; the framework downloads videos and files to local files to play or preview them, and lays out several media in one message as an album grid. A link preview carries the link's photos and videos (a shared post's), which the card shows large and pages through in place, so they can be looked through without opening the link; each network maps whatever large media its previews carry. A network that can load the post a link or attachment names shows it as a post instead (`ChatPost`): in a frame, the author's picture, name, verified badge, handle and time, with the network's icon (`ChatKit.networkIcon`) in the corner; the whole text, twelve lines until tapped open; the media paged through like a link preview's; the post it quotes, smaller, in a frame of its own; and its replies, reposts and likes along the bottom, in X's compact form ("1.2K", "12K"), each only when the network gives it. Tapping the author or the quote opens it on its network. A post is drawn by the kit rather than as a link preview because a post has an author and a quote that a link's title and description can't hold, and one look serves every network's posts.
- System rows (`ChatUser.isSystem`) are centered captions; one with a `.card` embed draws it there as its symbol and title in the tint color over its subtitle, opening its link when tapped, such as a thread's card where it was started in its parent chat (the adapter renders it as a notice).
- The chat screen and its state: connection state, history paging (earlier, and later for windows that don't reach the newest message), jumping to a message, searching the loaded messages (paging back for older matches), day sections with pinned date chips, the "New Messages" divider, unread count, replies, reactions, mentions, typing names, composer and draft.
- Behavior: optimistic sending and the outbox (see Sending), drafts per chat, polling or following pushed updates, debounced read markers, unread counting from the adapter's read position, the local store every chat reads from and loading the Chats list's chats ahead into it (see Storage), and in-chat links.
- Keeping the list still: a message that changes size (an edit, a link drawn as the post it points at once that loads) moves nothing else on screen. At the bottom the list follows the bottom; elsewhere the message at the top of the screen keeps its place. Multi-line labels in a bubble (the text, a post's text) are given their wrapping width before the first measurement, since a new label measures its lines at no width, sizing the cell too tall. Marking read on scroll only goes through history when a newer message is on screen; adapters should answer `isAfterReadPosition` from memory: it is asked per message.
- The Chats list: rows from every network merged newest first, archived rows apart, a cached list at launch, a network that fails keeps its previous rows, and an open chat keeps its row current. A row can show a thumbnail of its latest message's photo or video before the preview, as Telegram does (`ChatSummary.previewThumbnailURL`): the provider sets it, and an open chat's row takes it from its latest message's embeds (`ChatEmbed.previewThumbnailURL`).

**Adapter (per network):**

- A conversation adapter, with no UI state: says what the chat is (title, subtitle, whether names head bubbles); fetches pages of its network's history as records (newest, before a cursor, and with windows after a cursor and around a message) and renders stored records as framework messages; names a poll interval or follows pushed updates; sends text and attachments and returns the network's id for the message; reports the read position its network confirmed and says how to move it (moving it only once the network accepts the mark); keeps its per-chat state (names, read positions) for the next visit; writes what arrives outside a page (live updates, sent messages, the result of an action) to the chat's stored history. Optional abilities, each its own protocol so the screen offers exactly what the adapter implements: editing the user's messages (which ones, and from what text), reactions, the only emoji a network takes as reactions (so the picker offers just those), read receipts (whether each of the user's messages is sent or seen by someone else), audio previews, live updates and a lost connection, quoted messages outside the loaded ones, windows of older history around a message, typing, mentions (written as `@user_id` in the text and matched by a pattern, or marked by position on each message for networks whose mentions are entities), custom emoji (images for `:name:` keys in text and reactions), buttons on messages that ask the network to act (such as a bot's inline keyboard; link and copy buttons need no adapter), sticker sets, stickers for an emoji and sending stickers, sending voice messages (the framework records them and hands over the recording, its length and waveform; the adapter encodes what its network takes; without the ability, a chat that takes files gets the recording as an M4A file), forwarding natively (a reference to one of its messages, and forwarding a reference from another chat of the same account into this one), commands, in-chat links (links into the chat itself, and links and references such as `#room_id` that read as the place they name), and a composer menu (a setting of the chat, such as the model an assistant answers with: an icon at the end of the text row opens a menu headed by the current value; the button sits outside the input pill's glass, over a slot in the row, because a menu grows out of the glass its button is in and the whole pill would turn into the menu), muting and archiving the chat on its network (whether it is muted or archived comes from its Chats row, so a chat without one offers neither; once the network accepts a change the row changes at once, muted or moved between the list and the archive, and the next load confirms it; the app shows them on its chat details screen), and stopping in-flight work (while the adapter is busy, such as an assistant still answering, the composer's send button becomes a stop button in its place; tapping it tells the adapter to stop). Screens a network adds (member lists, profiles) have their own view models. Whether the network allows reactions, attachments or writing at all (`acceptsReactions`, `acceptsAttachments`, `isReadOnly`) may only be known once the adapter connects, which can be after the chat opens (stored messages that are current need no fetch), so the framework reads them again on every `onChange` while the chat is open.
- A list provider: the network's rows for the main list and the archive, and live row updates when the network pushes them. Optionally, it resolves a chat a notification or link names when no row has exactly that destination: matching its own rows on less than the full destination, or standing in for a chat the list doesn't have yet.
- A destination (the network's id for a chat) that one switch in the Chats screen turns into an adapter and the chat, or into why it can't open (not connected, locked).

**Forwarding:** a forward is the source message as displayed, its network and account, the adapter's native reference (if it gives one) and its media as fetchable files. The screen that opened the chat supplies where it goes (a chat picker), opens the target and stages the forward in its composer. The target forwards natively only when it is the same network and account and its adapter forwards; otherwise the framework sends a copy through the target's ordinary sends: an italic "Forwarded" line linking to the original where the source has message links (plain where the target has no formatting; no sender or network) with the text and first file, then each further file, voice messages through the voice send where the file decodes. Incoming forwards carry a forward origin (a name, or none when the network doesn't say) that the bubble shows.



**Voice transcripts:** every chat with voice messages offers a transcribe button beside the waveform on iOS 26 and later, with the text under it. Transcription is the framework's, on the device, through the audio file `audioPreviewURL(for:)` resolves; no adapter is involved and nothing leaves the device. It uses `SpeechTranscriber` where the device runs it and knows the language, else `DictationTranscriber`, which knows more languages. Neither detects the language, so a message is transcribed in each of `ChatKit.transcriptionLanguages` (the user's preferred languages by default), stopping at the first that is confident, and the result kept is the most confident one that `NLLanguageRecognizer` reads as the language it was transcribed in. Confidence alone picks wrongly: a Spanish model transcribes English almost perfectly and can be more confident about it (measured on the Mac, 2026-11-22). Below a score of 0.55 the bubble says it couldn't make the message out rather than showing the nearest language's fluent but wrong text: a language the device doesn't know, such as Afrikaans, which no Apple engine transcribes, comes out as confident-looking Dutch or English (real English notes scored 0.71–0.88, Afrikaans ones at most 0.45). Whisper does Afrikaans, but only its large models usably (`small` wrote a Dutch–Afrikaans mix), which are too big and slow for a phone. A long press on the button picks the language by hand. The first transcription in a language downloads its model (30–90 s on the Mac); after that a note takes well under a second. Audio is converted to the analyzer's preferred format, since `DictationTranscriber` takes no decoded Opus or AAC as it is. Transcripts are kept in the store (`voice_transcript`, by chat and message id, since a preview id can change: Telegram's names a file reference the network replaces) and removed with the account or history. Each transcription reports `ChatEvent.voiceTranscribed` (network, whether the language was chosen by hand, and the error when there is no transcript). The simulator can't transcribe (no compatible audio format, observed 2026-11-22 on iOS 27); the button says so. Showing or hiding a transcript is the user's own doing, like a scroll: it releases the list's hold on the "New Messages" divider (held after opening on unread messages until the user scrolls), so a transcript on the newest message grows upward above the composer instead of under it.

**Search on a Mac:** searching a chat shows a plain field under the bar instead of the system search field, whose presentation throws in an iPad app on macOS 27 (observed 2026-11-17). Temporary: try the system field again with each new iOS/macOS release.

**Messages on a Mac:** there's no long press. A click and drag selects a message's text (Command-C copies it), through an invisible text view over the bubble's label, the same way the lifted overlay makes its text selectable. Every right-click on a bubble lifts it into the overlay: the Mac sends right-clicks only to context menus, so the list's context menu lifts the message instead of showing a menu, and the text view passes right-clicks through so its own menu never shows. The lift starts at full size and doesn't bounce (a long press shrinks the bubble first and springs it out), and closing fades the blur, whose effect doesn't animate away on a Mac. Everywhere, a lifted bubble is 5% larger, growing away from its side of the screen.

**Rules:** shared code never names a network or casts to one; a network-specific need becomes an optional capability any network could use; every declared capability is implemented (no silent no-ops); adapters are tested against recorded pages without the UI.

## Storage

The screen reads only from the store; the network only writes to it (as Telegram's apps do, where opening a chat never waits). `ChatStore` is one SQLite database (the system library) for every chat, kept indefinitely; an app shares it with an extension through an App Group (`ChatKit.store`, with a Darwin notification name so each process sees the other's writes).

- **Records.** An adapter's page is records: its network's own message model, encoded, with an id, a sort key (the network's increasing id or a timestamp; ties by id) and a version (a stored record is replaced only by the same or a greater one, such as an Apron snapshot's `log_id`). A record that is an event about another message (an X Chat reaction or edit) relates to it, is read whenever it is and never bounds history. The adapter renders records, so how a message looks follows its current state (names, channel names), and keeps what actions need (albums, quoted originals). The kit never decodes them.
- **Chunks and gaps.** History is a list of chunks, runs known to have nothing missing, with a gap between two that the newer one's earlier cursor fills, as the Matrix SDK keeps it: networks page with opaque cursors and timestamps, so gaps can't be id ranges as in Telegram. A page joins the chunks its covered range overlaps (and the one it continues), and messages it covers but lacks were deleted, unless the network reports deletions as tombstones (`ChatPage.isComplete`). A record outside the covered range (an old message edited within the page's time) only updates its stored copy, except a message that moved into the chat from another, such as into a thread (`ChatPage.movedIn`, and `movedIn` on a live write): it keeps its old sort key, so it goes with the stored chunk that key falls in, else with the page's chunk (live: a current newest chunk, else the next page brings it). A `.before` page's continued chunk is never taken as its earlier edge, since moved messages can reach below the page. A newest page that overlaps nothing starts a newer chunk above a gap.
- **Freshness.** Each account has a sync epoch, new at launch and raised when updates may have been missed (a connection lost, caught up, or a chat closed without the app's sync following the account, `ChatStore.setFollowed`); going to the background raises every account's (`ChatStore.raiseEpochs`), since live connections stop there. The newest chunk records the epoch it was last known current in; a live record in that epoch continues it, a later one starts a chunk above a gap. A Chats row names its latest message (`ChatSummary.latestMessageId`); a newest chunk holding it is current, re-stamped without fetching. That holds only for a row the network built since the app was last in the background: rows from the cache at launch, or from before the background, may be behind, so a chat opened from one (typically from a notification about a newer message) and loading ahead ignore their latest message until a load or a live reload rebuilds the row. Otherwise a chat read before the background would open on its stored messages and never fetch the ones the notification is about.
- **Opening.** The chat reads ~60 messages from the store when made, going back while all are unread so it opens at the divider, and draws them in the first frame. It fetches the newest page only when the store isn't current, and the window follows new messages (moving to a newer chunk when one starts above it). Until it has connected, the divider follows what history is about to show: placed when the stored messages had no unread, moved up to unread messages the fetch brings before it (those under a message a push stored), never down; and it changes before the messages that move it, so the list moves once, straight to the divider. The view applies each published change at once, so a divider placed after the fetched messages reached the screen as a second move, after the list had followed the bottom (a frame at the new cells' estimated heights, then a 300 ms slide). In the list, only messages after the last one shown slide in at the bottom; messages a fetch inserts before it are placed without animation, and earlier history inserted while the divider is held at the top keeps the divider still rather than the distance from the bottom, which moved it down and back as the new cells were measured. Scrolling reads further chunks, and a gap fills from the network as the window reaches it; jumping reads a stored message's surroundings, or fetches a window around it where the adapter can (`ChatWindowing`), or pages back. Quotes of messages outside the window come from the store first; the adapter renders each on its own, then the window again, because a render replaces what the adapter keeps (reactors, your reactions, names) and that must be the window's.
- **Reading.** The newest message fully on screen is read while the chat is visible and the app active. The count and the divider drop at once, and the Chats row once the list stops scrolling (or the chat closes): each report rebuilds the whole Chats list (sorted, cached to disk, loaded ahead, redrawn), which costs more than a frame, so reading message by message while scrolling made the chat stutter. The framework keeps what the user read itself, because the adapter's position follows only what the network confirmed. The mark goes at once; while one is on its way, only the newest read since goes after it (a burst sends at most two), replacing the retries of a failed one. A failed mark is retried after 3 s and 15 s when it fails, and after that goes again with the next read, including on a later visit, since the adapter never moved past what the network accepted. A message seen before the chat connects is read once it has, so leaving early still reads it, while stored messages shown early don't move the position before history places the divider. An open chat reports its row (latest message, counts) to the Chats list, which keeps that over a rebuilt row naming the same latest message (a live reload of the rows, or a load that began before the report): the network built it before the user's read mark landed. A row naming a newer message is the network's, and the open chat fetches the newest messages when it doesn't hold that one, so what the row counts unread is on screen to be read. A chat reports only once it has connected, since its stored messages may be behind the row (an older latest message, a read position from before), and once per change: new messages and their unread count go together, never the new messages with the old count.
- **Provisional records.** A message known before its network's copy, such as one a push brought, is written provisional (`writeProvisional`): it shows after the chat's newest stored messages but never counts as stored history, so the chat still fetches, and the network's copy, or a page that covers it (or reaches the newest message) without it, replaces it. A chat whose newest chunk holds one is never current, even when its row's latest message is stored: newer messages from the network can be stored around a pushed one (observed with Apron, two of three pushed messages stored live and the third left provisional), and counting the chat current left it unconfirmed for good. A newest page accepts those older than it reaches in the history it joins as stored, since fetching again can't confirm them and waiting would fetch on every open.
- **Change notifications.** Writes notify the chat's observers on the main actor. A store shared with another process posts a Darwin notification, and reloads every observed chat only when SQLite's `data_version` shows the write was another connection's: hearing its own writes had redrawn every chat on each one. The store observes the notification without retaining itself and stops in `deinit`, since its own write's notification arrives after a store opened for one write (an extension's) is released. A chat reads the store and starts observing it only once shown (`prepareToShow()`, which the chat screen calls before its first render, and `connect()`), so chats made to load ahead decode nothing; pages are stored off the main thread.
- **Loading ahead.** Given a `prefetcher` (the app builds a row's chat, as it would to open it), `ChatListViewModel` keeps its first `prefetchLimit` (30) rows loaded whenever the list changes (unmuted before muted, unread before read, then newest), 3 at a time, each given up after 20 s, skipping rows whose latest message is stored, and loading one row at most every 20 s. Nothing is marked read, followed or polled. Apps keep rows live (their latest message) so changed chats load before they're opened.

## Images

`ImageCache` keeps decoded images in memory by URL and by key. Avatars (`CachedAsyncImage(persist: true)`, `ChatAvatarImage`, the avatars beside bubbles) are also kept on disk, stale-while-revalidate: once seen, an avatar draws in the first frame on every later launch, even when the network signs a new URL for the same picture (found by a stable key), and is downloaded again at most once a launch, replacing what shows only when it arrives. Loading ahead (`preload(url:key:persist:)`) reads and decodes kept avatars off the main thread.

## Sending

Every send goes through the store's outbox first: before the chat connects it waits there, shown as sending, and goes once it does; while connected it is kept there until the network answers, so a send the app closed on goes back to the composer rather than possibly twice. A chat opened again while an earlier visit is still sending (left and reopened before the network answered) leaves that send to it, rather than taking it for one the app closed on. The composer never waits for the chat to load.

`ChatViewModel` owns optimistic sending for every network. Networks publish their messages as `history`; `messages` is `history` followed by the user's messages still sending (`ChatMessage.isSending`). Every one of the user's messages has a status slot after the time, the same width for each state: a clock while sending, one check once sent, two once seen where the network reports receipts (`ChatReadReceipts`). The check takes the clock's place, so the bubble keeps its size when the network confirms it. A message sent from the composer grows out of the send button: a copy of its bubble starts as the button's circle above the composer and moves to where the bubble settles, as in Messages, rather than the list's insert sliding it up from behind the composer's glass. Sending clears a reply, edit or attachments just before the message arrives, so the composer shrinks first: it is laid out before the list follows the bottom, with the list held where it was, so the list moves up once to the composer's new top instead of dropping to it and then sliding up. `sendOptimistically(text:attachment:replyToId:deliver:)` adds the sending copy (a picked image is written to a temporary file and shown from it), clears the composer, and runs the network's `deliver`, which sends and returns the network's id for the message. The copy stays until a message with that id is in `history` (Apron's broadcast, Telegram's refresh, the copy Instagram and Spotify add), so it never blinks out; the confirmed message then keeps showing the picked image (`pickedImages`), so the swap doesn't reload the image or change its size. A failure removes the copy and puts the text and attachment back in an empty composer. The composer stages up to `ChatViewModel.maxAttachments` (10) files, picked several at once from the attachment sheet (in pick order), Files or a drop; they send as one message each, all shown as sending at once and delivered in order, the first carrying the text and the reply. A failure stops there, takes away the copies not yet sent and puts their files (and the text, if the first failed) back. Networks with albums could take them together through an ability of their own; none does yet. A sticker (`ChatStickerSending`) goes the same way, shown as itself, but leaves the draft alone. Apron commands don't use it, since a command may post nothing.

The composer's attach button opens the attachment sheet (`ChatMediaPicker`), as tall as what it shows: a strip of the user's recent photos (PhotoKit) to pick from, numbered in pick order, and rows for the camera (only where the device has one) and Files. The top bar's trailing button opens the system photo picker (All Photos) for albums and search until something is picked, then adds what's picked. Pulled up to full height, the strip becomes a grid of the recent photos, keeping what's picked, and the rows go until the sheet comes back down. Without access to the photo library a row asks for it in the strip's place; the system picker and Files need no access, so they still work. Picked photos are staged as the system picker's are: GIFs as they are, so they stay animated, anything else as JPEG.

Editing works the same way (`editOptimistically`): the edited message shows the new text at once, and keeps it until `history` changes the message (the network's copy may read differently, such as Telegram's mentions); a failure shows it as it was and puts the edit back in the composer. While editing, the composer's draft, attachments and reply are put aside, and the edit's text is never saved as the draft.

## Stickers

Stickers are drawn by the kit, with no dependency (`Sources/StupidChatKit/Stickers`):

- **Lottie (TGS):** `LottieAnimation` parses the gzipped Lottie JSON and `LottieRenderer` draws a frame with Core Graphics. It follows Telegram's rlottie fork (`TelegramMessenger/rlottie`, what Telegram's apps drew stickers with) rather than the Lottie spec where they differ, so stickers look as they do in Telegram: no skew, merge paths, expressions, effects or masks; rlottie's approximate distances for motion paths and trims; its gradient stops; and its unmasked colour packing, which some emoji rely on. Correctness is measured against rlottie frame by frame (`scripts/lottie-compare.py`) over a corpus of real stickers (stupid-social's `scripts/telegram-client.py sticker-corpus`, kept out of the repository), with the feature census in `scripts/lottie-census.py`.
- **Video (WebM):** `WebMSticker` reads the Matroska container (VP9 frames, each with its alpha as a second VP9 frame in the block additions) and decodes both with VideoToolbox's VP9 decoder, which iOS 26.2 lets apps register; the alpha frame's luma becomes the alpha. Checked against ffmpeg's libvpx decode (`scripts/webm-compare.sh`).
- **Playback:** as Telegram's apps do, frames are prepared ahead on a background queue, shown in order at the sticker's own frame rate (up to 60) only while on screen, and kept LZ4-compressed after the first loop, shared by every view showing the sticker at that size; grids such as the picker show first frames.
